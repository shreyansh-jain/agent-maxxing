# Writing Agent Context Files

An agent context file loads into every session, so every line in it costs tokens and attention. It should contain only facts the agent can't cheaply discover by itself, and each one must be verified.

## When to use

- Creating an agent instruction file for a repo, or updating one after the tooling changed
- An existing file has grown long, stale, or contradictory
- Agents keep repeating a mistake that a one-line rule would prevent, such as using the wrong package manager, editing generated files, or running the full suite
- A monorepo subtree has different commands and needs its own nested file

**Not for:** ADRs and user-facing docs (use `documenting-decisions`); writing skills (use `authoring-skills`); a one-off handover between sessions (use `handing-off-sessions`).

## Process

1. **Pick the file layout.** `AGENTS.md` at the repo root is the cross-tool standard: Codex, Cursor, Copilot, Gemini CLI, OpenCode and others read it. Claude Code reads `CLAUDE.md`, so give it a `CLAUDE.md` that contains the single line `@AGENTS.md`, or make it a symlink. Never maintain two diverging copies. Add a nested `AGENTS.md` only where a subtree has different commands or rules, keep it shorter than the root file, and don't repeat root rules in it. The closest file wins.
   Exit: one source of truth per scope.

2. **Inspect before writing.** Read the lockfiles and manifests (package manager), `package.json` scripts, the `Makefile`, task runners, and CI workflows (the commands that actually run), plus README, CONTRIBUTING, and `docs/`. Note generated files, vendored code, legacy areas, and anything CI does that a local run does not.
   Exit: you have a list of candidate facts, each tied to the file it came from.

3. **Keep only what passes the filter.** For each candidate line, ask: *would a capable agent get this wrong without being told, and can it not find out cheaply by reading the repo?* Keep it only if the answer is yes. Typical survivors:
   - The exact package manager, and the narrow commands: one test file, one lint target, typecheck
   - Commands that must *not* be run, or run only a certain way (e.g. "never run the full e2e suite locally")
   - Generated files and the command that regenerates them
   - Traps that have actually happened: a surprising env var, a required service, a flaky area
   - Where the deeper docs live, as a path table, instead of copying their content in

   Cut: linter or formatter rules the tooling already enforces, generic advice ("write clean code"), directory tours the agent can `ls`, lists of installed skills, and welcome text.

4. **Write it tight.** Use headings, bullets, and tables, with one rule per bullet. Put commands in a table. Use repo-relative paths. Target under 60 lines at the root and never exceed 100. Nested files should be shorter still. Give a reason only where it prevents a likely mistake.

5. **Verify every command and path.** Run each listed command once, or its `--help` if running it is expensive or the user's instructions forbid it, and confirm each path exists. Remove anything you could not verify, or ask the user about it.
   Exit: every line in the file is true today.

6. **When updating, prune.** Delete stale lines, merge duplicates, and resolve contradictions between the root and nested files. Don't reword the user's own rules without asking. Show the diff and the line count before and after.

## Output

```markdown
# Agent instructions

## Commands
| Task | Command |
|---|---|
| Install | `pnpm install --frozen-lockfile` |
| Typecheck | `pnpm tsc --noEmit` |
| One test file | `pnpm vitest run path/to/file.test.ts` |

## Rules
- Never run `pnpm test` without a path: the full suite needs the docker stack.
- `src/gen/` is generated by `pnpm codegen`; do not edit by hand.

## Where things are
| Need | File |
|---|---|
| Architecture | `docs/architecture.md` |
| Release process | `docs/releasing.md` |
```

## Red flags

- A command in the file that you never ran or checked
- Content copied from the README instead of linked
- The file grows past 100 lines, or a nested file repeats root rules
- Separately edited AGENTS.md and CLAUDE.md with different content
- Rules that restate what the linter or typechecker already enforces
